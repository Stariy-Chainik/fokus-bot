# Каталог бизнес-правил fokus-bot

Человекочитаемая спецификация домена, извлечённая из кода по ходу рефакторинга.
Формат: **правило** — где реализовано (файл/функция) — пояснение. Это описание **текущего** поведения (эталон для тестов), а не пожелания.

## Роли и доступ
- **Три роли:** admin, teacher, client (родитель). Определяются по `User.is_admin` и `User.teacher_id` — [bot/models/entities.py](../bot/models/entities.py). Пользователь загружается по `tg_id` в `AuthMiddleware`.
- **Спецроли убраны — все педагоги равны в правах** (bot/staff.py удалён). Раньше были: «Клецова» (прокси-запись за других) и «Контарева» (личный биллинг по своим группам).
  - Запись за педагога осталась **только у админа** («📝 Отметить занятие» → выбор педагога).
  - Выставление счетов — общая админская фича «🧾 Счёт ученика за период» ([admin/bills/](../bot/handlers/admin/bills/)): на экране группы — рассылка **всей группе** или счёт **отдельному ученику**.

## Зарплата педагога
- **`earned = round(rate × duration_min / 45)`**, количество учеников не влияет — [bot/services/billing_service.py](../bot/services/billing_service.py).
  - `rate = rate_group` для группового занятия, `rate = rate_for_teacher` для индивидуального.
- Единица нормирования — **45 минут** (`MINUTES_PER_UNIT` в [bot/utils/constants.py](../bot/utils/constants.py)).

## Счёт ученика (сумма к оплате)
- **Индивидуальное занятие:** `base = round(rate_for_student × duration_min / 45)`, делится **поровну** между участниками (слоты student_1..4), **целый остаток достаётся первому** ученику — [billing_service.py](../bot/services/billing_service.py). Для пары сумма двух строк точно равна полной стоимости.
- **Групповое занятие PER_VISIT:** сумма — снапшот в `attendees` (`STU-001:60:700`); биллится каждый ученик с `amount > 0` — [billing_service.py](../bot/services/billing_service.py).
- **`amount = 0` у ученика в группе = абонемент** (не биллится, не «пробное») — [attendees.py](../bot/utils/attendees.py).
- Виртуальные billing-строки **не хранятся** — считаются on-demand из Lesson + Teacher.

## Режимы биллинга групп
- `NONE` — бесплатно, посещаемость не тарифицируется, групповое занятие сохраняется с `attendees=None`.
- `PER_VISIT` — каждое посещение по цене группы (`price_full` / `price_short`).
- `SUBSCRIPTION` — **абонемент: фиксированная `price_full` ₽/месяц с каждого ученика группы,
  количество занятий не влияет** — [payment_service.py](../bot/services/payment_service.py)
  (`_subscription_bills_for_student`). Правила:
  - начисляется всем ученикам группы за месяц, в котором у группы было **хотя бы одно занятие**
    (каникулы/простой — не платят); посещал ли конкретный ученик — не важно;
  - присутствующих не отмечают — занятие сохраняется как у `NONE` (`attendees=None`);
  - в счетах/долгах начисление идёт под синтетическим ключом **`SUB:{group_id}`**
    (`teacher_id` инвойса), имя — «Абонемент «{группа}»»; включается админом в карточке
    группы → «Биллинг ученикам» → «💳 Включить абонемент»;
  - **цену можно переопределить на конкретный месяц** — для одного ученика или всей группы
    (лист `subscription_overrides`; UI там же, в «Биллинг ученикам»). Приоритет:
    **цена ученика на месяц → цена группы на месяц → `price_full`**; `amount = 0` =
    в этом месяце не начислять (освобождение) — [payment_service.py](../bot/services/payment_service.py)
    (`_sub_amount`);
  - **смена базовой цены действует только вперёд**: при изменении цены (и при включении
    абонемента) админ указывает, **с какого месяца** она действует; все прошлые месяцы
    с занятиями автоматически фиксируются переопределениями — старой ценой (при смене)
    или 0 (при первом включении: раньше абонемента не было) — `pin_subscription_history`.
    Ручные переопределения прошлых месяцев при этом не перезаписываются;
  - **выручка («📊 Прибыль»)** включает абонементы отдельным блоком с разбивкой по группам
    (`subscription_revenue_breakdown`); только в месячном виде — дню фикс-сумма не атрибутируется.
- **Прибыль (месяц)** = (занятия + абонементы + **прочие доходы**) − (зарплата + **расходы**).
  Прочие доходы (турниры и т.п., произвольные суммы и периодичность) и расходы (аренда и др.)
  админ вводит вручную на экране «📊 Прибыль» (➕ Доход / ➕ Расход за просматриваемый месяц);
  лист `finance_entries`, модель `FinanceEntry` — [finance_entry_repo.py](../bot/repositories/finance_entry_repo.py).
  Доменный результат формирует [ProfitService](../bot/services/profit_service.py); Telegram-хендлер
  только форматирует DTO.
- **PER_VISIT группы (снимок production-конфигурации):** GRP-0007, GRP-0008, GRP-0010,
  GRP-0015, GRP-0017, GRP-0018. Источник истины — `groups.billing_mode`; режим остальных групп
  нельзя выводить из этого списка.

## Тарифы SHORT/FULL
- Деление `price_short`(dur 35) / `price_full`(dur 60) — только детсадовские группы ЮБ/БП; у остальных одна цена — [entities.py](../bot/models/entities.py), `StudentGroupTier` [enums.py](../bot/models/enums.py).

## Сдача периода (блокировка)
- Педагог сдаёт период (разрешено с **25-го числа месяца**); после сдачи **не может** редактировать/удалять свои занятия в этом периоде.
- Строка `TeacherPeriodSubmission` используется как **замо́к**.
- **Админ (и вызовы с `bypass_period_lock=True`) обходят блокировку** — могут создавать и удалять занятия в сданном периоде. Переоткрытие = удаление строки submission.

## Счета и оплаты
- **ИНВАРИАНТ: оплачено клиентом ≥ отмечено педагогом** (по количеству занятий; индивидуальные
  и групповые). Гарантируется **сдачей периода**: после сдачи педагог не может добавить занятие →
  счёт финален на момент оплаты → клиент платит за все отмеченные занятия, недоплата исключена.
  ⚠️ Правка админом уже **оплаченного** периода (добавление занятия в обход замка) нарушает
  инвариант — доначисления нет; **по регламенту в оплаченный период изменения не вносить**.
- Инвойс = `StudentPeriodPayment`, **один на `(student, teacher, period)`**; статусы `PENDING` / `PAID` — [entities.py](../bot/models/entities.py).
- `get_or_create_invoices_for_student_period`: при изменившейся сумме обновляет **только не-PAID** счёт — [payment_service.py](../bot/services/payment_service.py).
- `confirm_period` переводит все PENDING периода в PAID — [payment_service.py](../bot/services/payment_service.py).
- **Занятие, добавленное после оплаты периода, автоматически не доначисляется** (PAID-счёт не
  пересчитывается). В текущем боте нет автоматического дополнительного счёта; переоткрытие только
  teacher submission не меняет статус оплаты. Коррекция требует отдельного операционного решения.
- **Оплата занятия ✅ вычисляется на лету:** `(date[:7], teacher_id)` есть в payments со статусом PAID. У занятий нет поля оплаты.
- **Счёт администратора обходит проверку сдачи периода** — выставить можно в любой момент, сумма пересчитывается из текущих занятий.
- Фискальный чек (CloudKassir) отправляется при подтверждении оплаты, если сервис настроен и у клиента есть телефон.
- Способы оплаты (наличные / реквизиты / СБП / ЮКасса) видны только если сконфигурированы через ENV.
- **Webhook ЮКассы верифицируется:** телу запроса не доверяем — из него берётся только `object.id`,
  платёж перепроверяется через API ЮКассы; подтверждение только при реальном `succeeded` —
  [bot/handlers/client/payments.py](../bot/handlers/client/payments.py) (`process_yookassa_event`).
  `PAID` ставится ровно двумя путями: верифицированный webhook или подтверждение админа.
- **Долг ученика** (экран «⚠️ Должники») = начисления по всем занятиям минус PAID-оплаты по
  `(student, teacher, period)`; выставлялся ли счёт — не важно; `amount=0` (абонемент) в долг
  не входит — [payment_service.py](../bot/services/payment_service.py) (`compute_debt_map`).
  Текущий (незакрытый) месяц показывается админу с пометкой, но в напоминания родителям
  **не включается** — напоминаем только за закрытые месяцы (правило месячного закрытия).

## Видимость педагог ↔ ученик
- Педагог видит ученика ⇔ пересечение `teacher_groups ∩ student_groups` непусто — [bot/services/visibility.py](../bot/services/visibility.py). Таблицы `teacher_students` **нет**.
- Ученик может состоять в нескольких группах; биллинг агрегирует по всем за период.
- Одну группу могут вести несколько педагогов; занятие принадлежит `lesson.teacher_id`.

## Занятия
- **Денормализация имён:** `lesson.teacher_name`, `student_N_name` — снапшоты на момент создания; переименования историю не переписывают — [entities.py](../bot/models/entities.py).
- **Гард дублей:** соло (ровно 1 ученик) блокируется по `teacher + student + date` (`individual_lesson_exists`); групповые **не** блокируются (разные смены в один день); пары не блокируются.
- INDIVIDUAL занятие может содержать 1–4 учеников (разовые микрогруппы из солистов) — [entities.py](../bot/models/entities.py).

## Клиент vs Ученик
- Ученик занимается, клиент (родитель) платит — разные сущности: `student.client_id → Client`, `student.parent_tg_ids → list[int]` (доступ в бот).
- **Разделитель `parent_tg_ids` — `|`, не `,`** (RU-локаль Google Sheets портит числа через запятую). Парсер принимает и `,` для обратной совместимости.
- **Регистрация клиента:** первый ученик — напрямую; добавление второго требует одобрения админа (`client:add_child`).

## Идентификаторы
- Последовательные строковые ID: `TCH-/STU-/LES-/PAY-/SUB-/BRN-/GRP-/USR-/CLT-/FIN-`;
  генератор берёт максимум среди существующих, игнорируя некорректные — [bot/utils/ids.py](../bot/utils/ids.py).
