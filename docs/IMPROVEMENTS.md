# Идеи по улучшению работы бота (НЕ внедрять в рамках рефакторинга)

Замечено по ходу поведение-сохраняющего рефакторинга. Здесь только фиксация; реализация — отдельным решением после согласования.
Формат: **проблема/идея** — где (файл/функция) — предложение — риск/выгода.

## Надёжность

### I1. Гонка read-modify-write в Google Sheets
- **Где:** [bot/repositories/base.py](../bot/repositories/base.py) (`_find_row_index` → `_update_row`/`_delete_row`).
- **Проблема:** индекс строки вычисляется из кэша, затем идёт запись/удаление **по номеру строки**. Если между этими шагами другая операция удалит/вставит строку выше, обновление/удаление попадёт не в ту строку. При Google Sheets нет транзакций.
- **Предложение:** писать/удалять с матчингом по ID-ячейке (find по значению непосредственно перед записью) либо сериализовать записи на лист через per-sheet asyncio.Lock.
- **Риск/выгода:** средний риск (меняет механику записи) / высокая выгода (защита данных при конкурентных действиях админа и педагога).

### I2. Локеры от даблкликов не переживают перезапуск и не масштабируются
- **Где:** процесс-локальные `InProgressGuard` в `teacher/record_lesson/finalize.py`,
  `teacher/submit_period.py`, `admin/bills/_base.py`, `admin/debtors.py`.
- **Проблема:** гарды унифицированы и снимаются в `finally`, но остаются in-memory: теряются при
  рестарте и не работают между несколькими процессами.
- **Предложение:** после унификации (P2 рефакторинга) перевести на Redis-локи с TTL.
- **Риск/выгода:** низкий/средний риск / средняя выгода (устойчивость к рестарту, готовность к многопроцессности).

### I3. Занятие после оплаты периода не доначисляется
- **Где:** [bot/services/payment_service.py](../bot/services/payment_service.py) (`confirm_period` не переоткрывает PAID).
- **Проблема:** если занятие добавлено в уже оплаченный период, сумма молча не пересчитывается (задокументировано, но легко забыть).
- **Предложение:** при добавлении занятия в PAID-период уведомлять админа или создавать доп-счёт на дельту.
- **Риск/выгода:** низкий риск / средняя выгода (недобор денег школой).

## Производительность

### I4. N+1 чтения из Sheets — частично закрыт (рефакторинг 2026-09-13)
- **Где:** например, [payment_service.py](../bot/services/payment_service.py) загружает педагогов
  по одному (с локальным кэшем на время расчёта), а `StudentService.get_student_card()` собирает DTO
  из нескольких репозиториев.
- **Проблема:** число повторных чтений уже частично снижено сервисным слоем и TTL-кэшем, но при
  холодном старте сложные экраны всё ещё обращаются к нескольким листам.
- **Предложение:** предзагружать словари (teacher_id → Teacher) одним `get_all()`; агрегировать чтения.
- **Сделано:** занятия родителя, запись занятия (ученики, группы), группы ученика, экран занятия,
  названия групп в счёте, переопределения цены; `StudentService` (карточка, тариф), `visibility.teachers_for_student`,
  `PaymentService` (группы ученика, участники абонементных групп из карты членства).
  **Осталось:** `ProfitService.get_lesson_summary`/`SalaryService.lines_for` (скан занятий на каждого педагога),
  `parent_views.bills_periods` (ledger на ученика×месяц — по природе), `api/miniapp` (см. B6).
- **Риск/выгода:** низкий риск / средняя выгода (отзывчивость UI, экономия квоты API).

## UX

### I6. Несогласованное форматирование сумм
- **Где:** по всем хендлерам — соседствуют `{x} руб`, `{x} ₽`, `{x}₽` (без пробела); нигде нет разделителя разрядов (напр. `12000` вместо `12 000`).
- **Проблема:** пользователь видит валюту то как «руб», то как «₽», с разным отступом. Единый `format_money()` **нельзя** ввести механически в рамках поведение-сохраняющего рефакторинга — он изменил бы текст на экранах.
- **Предложение:** согласовать один формат (например, `1 200 ₽` с неразрывным пробелом и разделителем тысяч) и завести `bot/utils/format.py::format_money`, затем разово прогнать все места. Это отдельная UX-задача с намеренным изменением вывода.
- **Риск/выгода:** низкий риск (текст) / средняя выгода (единообразие, читаемость сумм).

### I7. Разрозненное подавление ошибок вокруг edit/delete сообщения — ✅ УСТРАНЕНО
- Широкие `except Exception: pass` в хендлерах удалены; ожидаемые ошибки Telegram ловятся как
  `TelegramBadRequest` в `common.py` и `client/my_bills/`. Отдельный `safe_edit()` пока не нужен.

### I8. Сокращение шагов FSM записи занятия
- `record_lesson` уже разбит на пакет по этапам мастера. Сокращение числа шагов остаётся отдельной
  UX-задачей: оно изменит привычный сценарий и требует согласования, а не механического рефакторинга.

### I9. `get_by_id` — линейный скан с пересборкой всех сущностей — частично (циклы убраны, кеш сущностей в репо не сделан)
- **Где:** все репозитории (`get_by_id` = `for x in await self.get_all()`), `BaseRepository`.
- **Проблема:** каждый вызов преобразует **все** строки листа в dataclass'ы, даже при тёплом TTL-кеше;
  в циклах хендлеров (`client/my_lessons`, `record_lesson/finalize`, `students/groups`) это CPU-N+1.
- **Предложение:** предзагрузка словарей `{id → entity}` в сервисах (I4) и/или кеш разобранных сущностей
  рядом с кешем записей в `BaseRepository`.
- **Риск/выгода:** низкий риск / средняя выгода (отзывчивость длинных экранов).

### I11. Архивная группа остаётся в списках записи revenue-share (флоу «индивидуальное» Яковлевой)
- **Где:** [record_lesson/flows.py](../bot/handlers/teacher/record_lesson/flows.py) — `_rshare_branches`, `_rshare_groups_in_branch`.
- **Проблема:** группы педагога читались через `get_by_id`, который находит и архивные; при рефакторинге
  поведение сохранено (`get_all(include_archived=True)`), но по смыслу архив должен исчезать и здесь.
- **Предложение:** отдельным решением фильтровать `g.archived` в этих двух местах.
- **Риск/выгода:** низкий риск / низкая выгода (только группы Яковлевой).
