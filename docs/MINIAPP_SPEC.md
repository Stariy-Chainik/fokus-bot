## 1. Что это за система

CRM для танцевальной школы: учёт **занятий**, расчёт **зарплаты педагогов** и **счетов родителям**,
приём **оплат**. Три роли: **администратор**, **педагог**, **клиент (родитель)**.

Ключевая особенность домена: **billing-строки не хранятся** — и зарплата педагога, и счёт ученика
**вычисляются on-demand** из занятий (`Lesson`) и карточки педагога (`Teacher`). Единственное, что
хранится по деньгам, — это факт выставленного/оплаченного счёта за период (`StudentPeriodPayment`).

## 2. Роли и аутентификация

Пользователь опознаётся по Telegram `tg_id` → запись `User`. Роль выводится из полей `User`:

| Роль | Условие | Права (кратко) |
|---|---|---|
| **admin** | `is_admin = true`, `teacher_id = null` | всё: педагоги, ученики, группы, счета, выручка, запись за педагога, обход блокировки периода |
| **teacher** | `teacher_id != null` (может быть и `is_admin=true`) | свои занятия, свои группы/ученики, сдача периода, своя статистика |
| **client** | нет `User`-записи админа/педагога; вход по `student.parent_tg_ids` | занятия и счета своих детей, оплата |

- **admin+teacher одновременно** — админ с привязанным `teacher_id`; в боте может переключать «режим».
- **Видимость teacher↔student** — не по прямой таблице, а по **пересечению групп** (см. §6).
- **client** — это Telegram-аккаунт, чей `tg_id` присутствует в `student.parent_tg_ids` хотя бы одного
  ученика. Отдельная сущность `Client` (тот, кто платит) может иметь свой `tg_id` и телефон.

Реализация в боте: `AuthMiddleware` грузит `User` по `tg_id` — [bot/middlewares/auth.py](../bot/middlewares/auth.py).
В Mini App аналог — валидация `initData` Telegram и резолв `tg_id` → роль на бэкенде.

## 3. Доменная модель (сущности и поля)

Источник истины — dataclasses в [bot/models/entities.py](../bot/models/entities.py),
энумы в [bot/models/enums.py](../bot/models/enums.py). Хранилище-агностично: поля ниже — это и есть схема.

### Энумы
- `LessonType`: `group` | `individual`
- `PaymentStatus`: `pending` | `paid`
- `RequestStatus`: `pending` | `approved` | `rejected`
- `GroupBillingMode`: `none` | `per_visit` | `subscription` *(абонемент: фикс `price_full` ₽/мес)*
- `StudentGroupTier`: `full` | `short`

### User
`user_id`, `tg_id:int`, `is_admin:bool`, `teacher_id:str|null`

### Teacher
`teacher_id`, `tg_id:int|null`, `name`, `rate_group:int`, `rate_for_teacher:int`, `rate_for_student:int`
— три ставки в **рублях за 45 минут**: групповая, индивидуальная (в зарплату педагога), и ставка для
счёта ученика.

### Client (родитель — тот, кто платит)
`client_id`, `name`, `tg_id:int|null`, `created_at`, `phone:str|null`

### Student (ученик — тот, кто занимается)
`student_id`, `name`, `partner_id:str|null`, `group_ids:list[str]`,
`group_tier:full|short`, `client_id:str|null`, `parent_tg_ids:list[int]`
- `partner_id` — **симметричная** связь пары (обе записи обновляются вместе).
- `group_ids` — ученик может быть в нескольких группах.
- `parent_tg_ids` — Telegram-аккаунты с доступом к боту/приложению (**разделитель `|`**, см. §4).

### Branch (филиал)
`branch_id`, `name`, `created_at`, `updated_at`

### Group (группа)
`group_id`, `branch_id`, `name`, `created_at`, `updated_at`, `sort_order:int`,
`billing_mode:none|per_visit|subscription`,
`price_short:int`, `duration_short:int=35`, `price_full:int`, `duration_full:int=60`
- Цены/длительности **short/full** используются только для детсадовских групп с dual-pricing (§6).

### TeacherGroup / StudentGroup (join-таблицы «многие-ко-многим»)
`TeacherGroup(teacher_id, group_id)` · `StudentGroup(student_id, group_id)`

### Lesson (занятие)
`lesson_id`, `teacher_id`, `teacher_name`*, `type:group|individual`,
`student_1_id/name`*, `student_2_id/name`*, `student_3_id/name`*, `student_4_id/name`*,
`date` (`YYYY-MM-DD`), `duration_min:int` (обычно 45/60/90), `earned:int`,
`recorded_at`, `updated_at`, `attendees:str|null`, `group_id` (только для групповых)
- `*_name` — **денормализованные снапшоты** на момент создания (переименования историю не меняют).
- **INDIVIDUAL** содержит 1–4 учеников в слотах `student_1..4` (разовая микрогруппа из солистов).
- **GROUP** — присутствующие кодируются в `attendees` (CSV, см. ниже); слоты `student_*` не используются.
- `earned` в строке хранится как `0` — фактическая зарплата **считается on-demand** (§7).

**Поле `attendees`** (только для групповых) — [bot/utils/attendees.py](../bot/utils/attendees.py). Два формата в одном поле:
- старый: `STU-0001,STU-0002` — только id; длительность = `duration_min` занятия, `amount = 0` (**= абонемент**, не биллится);
- расширенный: `STU-0001:60:850,STU-0002:35:500` — `id:duration_min:amount_снапшот(₽)`.
- Разделитель записей — запятая; поля внутри записи — двоеточие. `amount = 0` означает **абонемент** (не «пробное»).

### Billing (виртуальная строка счёта — НЕ хранится)
`billing_id`(пусто), `lesson_id`, `student_id`, `student_name`, `teacher_id`, `teacher_name`,
`date`, `duration_min`, `amount:int`, `period_month`(`YYYY-MM`), `payment_id`, `created_at`, `updated_at`,
`lesson_type` — вычисляется `build_billing_rows(lesson, teacher)` (§7). Модель существует только для формы данных.

### StudentPeriodPayment (счёт за период — хранится)
`payment_id`, `student_id`, `student_name`, `period_month`(`YYYY-MM`), `total_amount:int`,
`status:pending|paid`, `paid_at`, `confirmed_by_tg_id`, `comment`, `created_at`, `updated_at`,
`teacher_id`, `teacher_name`
- **Один счёт на `(student, teacher, period)`** (см. §8).

### TeacherPeriodSubmission (сдача периода = замо́к)
`submission_id`, `teacher_id`, `period_month`(`YYYY-MM`), `submitted_at`, `lessons_count:int`, `total_earned:int`
- Наличие строки = период **сдан** и заблокирован для педагога (§6).

### StudentRequest (заявка педагога на нового ученика)
`request_id`, `teacher_id`, `teacher_tg_id:int`, `teacher_name`, `student_name`, `group_id`,
`status:pending|approved|rejected`, `created_at`, `resolved_at`, `resolved_by_tg_id`, `admin_msgs_json`
- `admin_msgs_json` — JSON `[[chat_id, message_id], ...]`: адреса сообщений-уведомлений у админов (для их обновления после решения).

## 4. Хранилище: текущее (Google Sheets) и его подводные камни

Сейчас БД — **Google Sheets** (одна вкладка на сущность). Имена вкладок настраиваются через ENV
(§11), по умолчанию: `users`, `teachers`, `students`, `lessons`, `student_period_payments`,
`teacher_period_submissions`, `branches`, `groups`, `teacher_groups`, `student_groups`,
`student_requests`, `clients`. Столбцы идут в порядке полей сущности; строка 1 — заголовок, строки 2+ — данные.

**Подводные камни, которые обязательно сохранить при любой реализации:**
1. **Разделитель мульти-значений — `|`, не `,`.** RU-локаль Google Sheets трактует `,` как десятичный
   разделитель и портит числа (`"123,456"` → `123`). Поэтому `student.parent_tg_ids` пишется через `|`.
   Парсер принимает и `,` для обратной совместимости. (В `attendees` запятая используется намеренно как
   разделитель записей — там значения не числовые целиком.)
2. **Денормализованные снапшоты имён** (`lesson.teacher_name`, `student_N_name`) — это фича, не грязь.
3. **Неатомарность записи** (read-modify-write): чтение индекса строки и запись — раздельны; при
   конкурентной записи возможна гонка. В боте это гасят module-level локеры от даблкликов.
4. **Лимит ~60 req/min**, поэтому в репозиториях TTL-кэш (300 с) на чтение + retry с backoff на 429/503.
5. **Порядок и имена столбцов менять нельзя** без миграции данных.

> Для Mini App хранилище можно (и стоит) заменить на нормальную БД (Postgres). Тогда пункты 1, 3, 4
> снимаются на уровне БД (транзакции, нормальные типы), но **доменные правила §6–§8 должны остаться
> идентичными**. При переносе учесть оба формата `attendees` и снапшоты имён.

## 6. Бизнес-правила домена

### Видимость педагог ↔ ученик
- Педагог **видит** ученика ⇔ пересечение `teacher_groups ∩ student_groups` непусто —
  [bot/services/visibility.py](../bot/services/visibility.py). Прямой таблицы `teacher_students` **нет**.
- Ученик может быть в нескольких группах; счёт агрегирует по всем за период.
- Одну группу могут вести несколько педагогов; занятие всегда принадлежит `lesson.teacher_id`.

### Группы: режимы биллинга
- `none` — бесплатно/абонемент: посещаемость **не тарифицируется**; групповое занятие сохраняется
  сразу с `attendees=null` (без экрана отметки присутствующих).
- `per_visit` — каждое посещение по цене группы (`price_full`/`price_short`); в момент записи в
  `attendees` кладётся **снапшот** тарифа на каждого присутствующего.
- `subscription` — **абонемент**: фиксированная `price_full` ₽/месяц с каждого ученика группы,
  количество занятий не влияет; начисляется за месяц, в котором у группы было **хотя бы одно
  занятие** (каникулы — не платят); посещаемость не отмечается (`attendees=null`); в счетах/долгах
  начисление под синтетическим ключом `SUB:{group_id}` (в поле `teacher_id` инвойса).
  Цена переопределяется на конкретный месяц (сущность `SubscriptionOverride(group_id,
  period_month, student_id?, amount)`): приоритет **ученик → группа → `price_full`**;
  `amount = 0` = в этом месяце не начислять (освобождение).
- Текущие `per_visit`-группы: `GRP-0007, GRP-0008, GRP-0010, GRP-0015, GRP-0017, GRP-0018`; остальные `none`.

### Тарифы SHORT/FULL
- Деление `short`(dur 35, `price_short`) / `full`(dur 60, `price_full`) применяется **только** к
  детсадовским группам (ЮБ/БП) с dual-pricing; у остальных одна цена. Тариф ученика — `student.group_tier`
  (default `full`), переключается в карточке ученика.

### Занятия: запись
- **Дата в будущем запрещена** (`date > today` → ошибка) — [lesson_service.py:52](../bot/services/lesson_service.py#L52).
- **Гард дублей соло:** новое INDIVIDUAL-занятие отклоняется, если у любого из его учеников уже есть
  **соло** (ровно 1 ученик) INDIVIDUAL-занятие с тем же педагогом на эту дату —
  [lesson_repo.py:67](../bot/repositories/lesson_repo.py#L67). Парные/микрогрупповые (2–4 ученика) и
  групповые дубли **не блокируются** (одна группа может иметь несколько смен в день).
- **Типы записи:**
  - `group` — выбор группы → (для `per_visit`) отметка присутствующих с тарифом → одно GROUP-занятие;
  - `pair` — по одной INDIVIDUAL-записи на каждую выбранную пару (`student_1`,`student_2`);
  - `soloist` — по одной INDIVIDUAL-записи на каждого солиста;
  - `shared` — одно INDIVIDUAL-занятие на 2–4 солистов (счёт делится поровну); слоты канонизируются
    сортировкой по `student_id`.

### Сдача периода (блокировка)
- Педагог **сдаёт период** (`TeacherPeriodSubmission`) — после этого **не может** создавать/удалять свои
  занятия в этом периоде. Наличие строки submission = замо́к.
- Педагогу разрешено сдавать период **только с 25-го числа месяца**.
- **Админ и любые вызовы с `bypass_period_lock=true` обходят блокировку** — создают и удаляют занятия в
  сданном периоде. **Переоткрытие периода** = удаление строки submission.

### Клиент vs Ученик
- Ученик занимается, **клиент (родитель) платит** — разные сущности: `student.client_id → Client`,
  `student.parent_tg_ids → list[int]` (доступ в приложение).
- **Регистрация клиента:** первый ребёнок — напрямую (без одобрения); добавление второго — через заявку
  и одобрение админом.

## 7. Деньги: зарплата и счета (формулы)

Единица нормирования — **45 минут** (`MINUTES_PER_UNIT`). Всё считается on-demand —
[bot/services/billing_service.py](../bot/services/billing_service.py).

### Зарплата педагога за занятие
```
earned = round(rate × duration_min / 45)
  rate = rate_group        для group
  rate = rate_for_teacher  для individual
```
Количество учеников на зарплату **не влияет**. Зарплата за период = сумма `earned` по занятиям педагога.

### Счёт ученика (сумма к оплате)
- **Индивидуальное занятие:**
  ```
  base = round(rate_for_student × duration_min / 45)
  делится ПОРОВНУ между участниками (слоты student_1..4);
  целый остаток (base − (base//n)·n) достаётся ПЕРВОМУ ученику.
  ```
  Для пары сумма двух строк точно равна полной стоимости занятия.
- **Групповое `per_visit`:** сумма — снапшот из `attendees` (`STU-001:60:700`); биллится каждый ученик
  с `amount > 0`. `amount = 0` = **абонемент** (в счёт не входит).
- **Группы `none`** в счёт клиента не включаются.
- Счёт ученика за период агрегируется **по педагогам**: `dict[teacher_id] → {name, total, items}` —
  [payment_service.py:27](../bot/services/payment_service.py#L27).

## 8. Поток оплат

### Модель счёта
- Инвойс = `StudentPeriodPayment`, **один на `(student, teacher, period)`**. Статусы `pending`/`paid`.
- `get_or_create_invoices_for_student_period`: создаёт недостающие инвойсы; если сумма изменилась —
  обновляет **только не-PAID** счёт; PAID не трогает — [payment_service.py:55](../bot/services/payment_service.py#L55).
- `confirm_period` переводит **все PENDING** периода ученика в PAID —
  [payment_service.py:148](../bot/services/payment_service.py#L148).

### Ключевые правила
- **У занятия НЕТ поля оплаты.** Галочка «оплачено ✅» на экране занятий вычисляется на лету: существует
  ли для `(date[:7], teacher_id)` счёт со статусом `paid`.
- **Занятие, добавленное после оплаты периода, автоматически НЕ доначисляется** (`confirm_period`
  пропускает PAID). Решение: переоткрыть период или создать второй счёт вручную.
- **Счёт от админа / биллинг-педагога обходит проверку сдачи периода** — выставить/разослать можно в
  любой момент; сумма пересчитывается из текущих занятий при каждом открытии.
- В счёте родителю: оплаченные педагоги показываются с ✅ и исключаются из «К оплате»; «К оплате» = сумма
  только неоплаченных педагогов; кнопка «Оплатить» скрыта, если платить нечего.
- **Родителю не показываем статусы «период сдан/не сдан»** — он платит школе, а не следит за сдачей.

### Способы оплаты (видны только если сконфигурированы через ENV)
1. 💵 Наличные — уведомление админу + кнопка «Подтвердить» (`PAYMENT_CASH_ENABLED`).
2. 🏦 По реквизитам — QR + реквизиты; клиент загружает чек (`PAYMENT_BANK_DETAILS`/`PAYMENT_QR_*`).
3. 📱 СБП — реквизиты СБП; клиент загружает чек (`PAYMENT_SBP_DETAILS`).
4. 💳 Картой онлайн — ЮКасса, ссылка на оплату (`YOOKASSA_SHOP_ID`+`YOOKASSA_SECRET_KEY`).

### Подтверждение и фискализация
- При ручном подтверждении (наличные/чек) админ → `confirm_period()` → все PENDING периода → PAID.
- Если настроен **CloudKassir** и у связанного `Client` есть телефон — после оплаты отправляется
  фискальный чек на оплаченную сумму (иначе шаг тихо пропускается).
- ЮКасса-webhook подтверждает оплату по `metadata.student_id`/`period_month` (см. [payments.py](../bot/handlers/client/payments.py)).

## 9. Функциональность по ролям (use-cases)

Ниже — фронт-агностичный перечень: **актёр → действие → эффект**. (Реализация в боте — экраны/FSM; в Mini
App это станет страницами/формами/REST-эндпоинтами. Полный inventory с callback_data — в [CLAUDE.md](../CLAUDE.md).)

### Администратор
- **Педагоги:** список (со статусом сдачи прошлого месяца 🟢/🔴), карточка, добавить (tg_id → имя → 3 ставки),
  править ставки, править группы (чекбоксы), удалить (чистит `teacher_groups`), **переоткрыть сданный период**.
- **Ученики:** список с поиском (пагинация 20), карточка (группы/партнёр/клиент/тариф), добавить, переименовать,
  удалить (сначала снять партнёра), назначить/снять партнёра (симметрично, с откатом), привязать/создать клиента,
  переключить тариф short/full.
- **Пары/солисты по группам:** филиал → группа → список; создать пару, назначить ведущего.
- **Заявки педагогов** на новых учеников: одобрить (создать нового / привязать существующего) / отклонить.
- **Филиалы и группы:** CRUD филиалов; CRUD групп; педагоги группы (чекбоксы); режим биллинга и тарифы
  группы; **массовая рассылка счетов группе**; добавление/удаление ученика в группе (поиск/создание).
- **Счета:** инвойсы по ученику/периоду; отправка родителю (мультиполучатель), **без проверки сдачи периода**.
- **Зарплаты:** заработок по педагогам за период.
- **Выручка:** доход школы vs зарплаты (по дню или по периоду).
- **Занятия (правка):** педагог → дата/месяц/все → просмотр+удаление, **обход блокировки периода**.
- **Диагностика:** проверка консистентности (занятия-сироты на несуществующих педагогов/учеников).
- **Запись за педагога (прокси):** выбрать педагога → полный мастер записи, **обход блокировки**.

### Педагог
- **Запись занятия:** мастер тип(группа/пара/соло/shared) → выбор учеников/группы → дата → длительность →
  подтверждение. Для `none`-группы — авто-сохранение без отметки присутствующих.
- **Мои занятия:** фильтр сегодня/вчера/дата/месяц; переключение типа; пагинация; удаление (сданные
  скрыты для педагога, видимы админу).
- **Сдать период:** только с 25-го; показывает сводку (кол-во занятий + сумма) перед подтверждением.
- **Мои группы / пары / солисты:** ростер; карточка ученика/пары; переименование ученика; назначить/снять
  партнёра; занятия по ученику/паре (с помесячным выбором).
- **Моя статистика:** личный заработок.
- **(спецроль) Счета учеников** — только для биллинг-педагогов, строго по своим группам (§10).

### Клиент (родитель)
- **Регистрация:** первый ребёнок напрямую; **добавить ребёнка** — заявка на одобрение админом.
- **Мои занятия:** выбор ребёнка или «все вместе»; фильтр дата/месяц; ✅ на оплаченных.
- **Мои счета:** по месяцам со статусом; детализация счёта (по педагогам, оплаченные ✅, «К оплате» = сумма
  неоплаченных).
- **Оплата:** выбор способа (только сконфигурированные) → карта(ЮКасса)/реквизиты/наличные/СБП; загрузка чека;
  админ подтверждает.

## 10. Спецроли и конфигурация

Жёстко зашитые кадровые правила вынесены в одно место — [bot/staff.py](../bot/staff.py):

- **Клецова Ангелина (`TCH-0002`)** — ассистент: может записывать занятия **за** Никишина (`TCH-0005`) и
  Криворчук (`TCH-0008`) через прокси. Прокси-запись **требует одобрения админа**; админ прокси-записи не требует.
  Конфиг: `PROXY_BUTTONS = {"TCH-0002": [("…","proxy_record:TCH-0005"), ("…","proxy_record:TCH-0008")]}`.
- **Контарева Елизавета (`TCH-0009`)** — педагог с доступом к выставлению счетов, **строго по своим группам**
  (каждый callback перепроверяет `_can_bill` / `_is_my_group` / `_is_student_in_group`). Содержимое счёта — как
  у админа (по всем педагогам ученика). Конфиг: `BILLING_TEACHERS = {"TCH-0009"}`.

> В Mini App этот хардкод разумно превратить в **данные/флаги** (например, `teacher.can_proxy_for = […]`,
> `teacher.can_bill = true`) — поведение то же, но без правок кода при смене персонала.

## 11. Интеграции и переменные окружения

**Обязательные:** `BOT_TOKEN`, `GOOGLE_CREDENTIALS_JSON` (service-account JSON одной строкой), `SPREADSHEET_ID`.

**Имена вкладок** (`SHEET_*`) — необязательные, есть дефолты (§4).

**Оплаты:**
- `PAYMENT_CASH_ENABLED` (default `true`), `PAYMENT_BANK_DETAILS`, `PAYMENT_QR_DATA` (формат ЦБ РФ
  `ST00012|Name=…|PersonalAcc=…`), `PAYMENT_QR_IMAGE_URL`, `PAYMENT_SBP_DETAILS`.

  `PAYMENT_WEBHOOK_PORT` (default `8081`).
- `CLOUDKASSIR_PUBLIC_ID`, `CLOUDKASSIR_API_SECRET` — фискальные чеки; пусто → шаг пропускается.

иначе in-memory). Источник: [config/settings.py](../config/settings.py).

**Внешние интеграции:** Telegram Bot API (aiogram 3), Google Sheets (gspread), ЮКасса (карты онлайн),
CloudKassir (онлайн-касса/фискализация). Внешние файлы-источники (посещения, расписания) — **только на чтение**.

## 12. Воспроизведение в Mini App: что сохранить, что переосмыслить

**Mini App** = web-интерфейс внутри Telegram (React/Vue + бэкенд-API), аутентификация через `initData`
(подпись Telegram проверяется на сервере, `tg_id` → роль). Домен тот же — меняется только фронт и (по желанию)
хранилище.

### Обязательно сохранить 1-в-1 (это и есть «правила»)
- Все **формулы** §7 (единица 45 мин, `round`, деление поровну с остатком первому, снапшот `per_visit`).
- **Оба формата `attendees`** и правило `amount=0 = абонемент`.
- Модель счёта §8: один инвойс на `(student, teacher, period)`; обновляется только не-PAID; `confirm_period`;
  «оплачено» вычисляется по `(period, teacher)`, а не хранится на занятии; занятие после оплаты не доначисляется.
- **Блокировка периода** (сдача, замо́к submission, обход админом, сдача только с 25-го).
- **ИНВАРИАНТ: оплачено клиентом ≥ отмечено педагогом** (индивидуальные и групповые) — обеспечивается
  сдачей периода; правки в оплаченный период запрещены регламентом (доначисления нет).
- **Видимость** через пересечение групп (нет `teacher_students`).
- **Гард дублей** (соло блокируется, пары/группы — нет), запрет будущей даты.
- **Денормализованные снапшоты имён** в занятиях.
- Читаемые **ID** §5 (можно оставить).
- Разделение **Client vs Student** и порядок регистрации (первый — напрямую, второй — через одобрение).

### Стоит переосмыслить под web (без изменения домена)
- **FSM-мастера → формы/визарды** на клиенте; серверные эндпоинты вместо callback_data и состояний.
- **Хранилище → Postgres**: снимает RU-локаль/`|`-разделитель, гонки read-modify-write, лимит req/min,
  TTL-кэш и retry (всё это — костыли вокруг Google Sheets). Транзакции решают неатомарность инвойсов/партнёров.
- **Локеры от даблкликов** → идемпотентность/транзакции на сервере (создание занятия, сдача периода,
  подтверждение оплаты).
- **Спецроли** (§10) → флаги в данных, а не хардкод.
- **Способы оплаты** — та же логика «показывать только сконфигурированные».

### Модель данных для бэкенда (минимум таблиц)
`users, teachers, clients, students, branches, groups, teacher_groups, student_groups, lessons,
student_period_payments, teacher_period_submissions, student_requests`.
Билинг-строки **не таблица**, а вычисление (`build_billing_rows`). Зарплата — вычисление (`calc_earned`).
