**Пользователь явно попросил разделить:** «ученик занимается, клиент платит».

## Модель, к которой пришли

**Новый лист `clients`:**
- `client_id, name, phone, email, tg_id, created_at`

**`students` +1 колонка:** `client_id` (FK на clients)

**`student_invites` → `client_invites`:** код выдаётся клиенту, не ученику.

## Ключевые свойства

- Один клиент = один или несколько учеников (родитель с несколькими детьми)
- Взрослый, который платит сам → в `clients` и `students` две записи с совпадающим ФИО
- В Telegram привязывается клиент, не ученик
- После привязки клиент видит расписание и счета всех своих учеников (с фильтром/переключателем)
- Один инвайт-код привязывает клиента → автоматически получает доступ ко всем его ученикам

## 4 открытых вопроса перед реализацией

1. Клиент всегда один на ученика (не 50/50 двух родителей)?
2. Где сейчас хранятся телефоны/email клиентов (вне бота в CRM/голове)? Нужна миграция в `clients`?
3. Для существующих учеников — при выдаче первого кода бот запрашивает ФИО/телефон/email и создаёт `clients`?
4. Групповой инвайт: один код на клиента (подхватывает всех его учеников) vs отдельный код на каждого ученика. Склонились к первому.

**Why:** модель клиент/ученик принципиально отличается от предыдущих обсуждений ТЗ — там везде фигурировал «ученик как клиент». Это требует переделки:
- `student_invites` → `client_invites`
- инвайт-логики в `bot/handlers/client/auth.py`
- меню клиента с переключателем учеников
- привязки `tg_id` в `clients`, а не `students`

**How to apply:** при реализации клиент-роли этот файл — отправная точка. Сначала ответить на 4 вопроса, потом переписать ТЗ Этапа 1 с учётом разделения, только потом кодить.
