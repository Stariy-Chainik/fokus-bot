# Промпт: рефакторинг fokus-bot

> Скопируй всё, что ниже разделителя, и передай кодовому агенту (Claude Code / другому).
> Промпт заточен под конкретные проблемы этого репозитория — файлы и строки реальные.

---

## Роль и контекст

Ты — старший Python-инженер, которому поручили **поведение-сохраняющий рефакторинг** Telegram-бота `fokus-bot` (aiogram 3, CRM для танцевальной школы). База данных — **Google Sheets** (не Postgres): у неё лимит ~60 req/min, локаль RU ломает запятые в числах, и записи неатомарны. Продакшн крутится на VPS под systemd, деплой — `./scripts/deploy.sh`. **Тестов нет вообще** (`tests/` пустой). Архитектура и правила домена описаны в [CLAUDE.md](../CLAUDE.md) — прочитай её первой, это источник истины.

Отвечай и комментируй код по-русски; идентификаторы и технические термины оставляй как есть.

## Железные правила (guardrails)

1. **Не менять поведение.** Каждый пользовательский сценарий (тексты сообщений, набор кнопок, callback_data, порядок FSM-шагов, суммы в счетах) должен остаться байт-в-байт таким же. Рефакторинг ≠ фичи ≠ багфиксы ≠ улучшения. Всё, что замечаешь по ходу, но **не применяешь**, складывай в три отдельных файла (см. «Отдельные файлы-артефакты» ниже): баги → `docs/FOUND_BUGS.md`, идеи улучшений → `docs/IMPROVEMENTS.md`, обнаруженные бизнес-правила → `docs/BUSINESS_RULES.md`. Ничего из них не внедряй в код в рамках этого рефакторинга.
2. **Маленькими шагами.** Один коммит = одна изолированная замена. Никаких «переписал пол-файла». После каждого шага проект должен импортироваться и запускаться (`python -m bot` не падает на старте).
3. **Уважай специфику Google Sheets:**
   - Разделитель мульти-значений — `|`, **не** `,` (RU-локаль превращает `"123,456"` в `123`). См. `student.parent_tg_ids`.
   - Не ломай TTL-кэш и retry/backoff в [bot/repositories/base.py](../bot/repositories/base.py). Помни: read-modify-write (`_find_row_index` → `_update_row`) **неатомарен** — не создавай новых мест, где гонка между чтением индекса строки и записью может затереть данные.
   - Именование колонок листов и порядок полей в строках менять **нельзя** без миграции данных.
4. **Не трогай, если не уверен.** Денормализованные снапшоты (`lesson.teacher_name`, `student_N_name`), два формата `attendees` (старый `STU-001` и новый `STU-001:60:700`), формулы биллинга (`× duration_min / 45`) — это домен, а не «грязь». Сохраняй оба формата attendees.
5. **Не деплой сам.** Никаких `deploy.sh`, `ssh`, `systemctl`. Только правки в рабочем дереве + коммиты.

## Отдельные файлы-артефакты (создать и вести по ходу работы)

Рефакторинг сохраняет поведение, поэтому всё, что «хочется поменять», не меняем — **документируем** в трёх файлах. Заводи их сразу в первом коммите (пустые шаблоны с заголовками) и пополняй по мере чтения кода.

1. **`docs/BUSINESS_RULES.md` — каталог бизнес-правил.** Пока читаешь код, выписывай каждое обнаруженное доменное правило: как считается зарплата педагога и сумма счёта (формулы, деление на учеников, остаток), режимы биллинга групп (NONE / PER_VISIT / SUBSCRIPTION), тарифы SHORT/FULL для детсадовских групп, правила блокировки периода (сдача с 25-го, кто может редактировать после сдачи), правила видимости педагог↔ученик, гард дублей занятий (соло блокируется, группа/пара — нет), логика оплат и статусов PENDING/PAID, спецроли (Клецова-прокси, Контарева-биллинг). Формат: правило — где реализовано (`file:line`) — краткое пояснение. Это должно стать человекочитаемой спецификацией домена.

2. **`docs/IMPROVEMENTS.md` — идеи по улучшению работы бота.** Всё, что заметил и что улучшило бы продукт, но выходит за рамки поведение-сохраняющего рефакторинга: UX (навигация, тексты, лишние шаги FSM), надёжность (гонки при read-modify-write в Sheets, устойчивость к перезапуску, локеры без TTL), производительность (лишние чтения листов, N+1 по репозиториям), наблюдаемость, безопасность. Формат: проблема/идея — где (`file:line`) — предлагаемое улучшение — оценка риск/выгода. **Не реализовывать.**

3. **`docs/FOUND_BUGS.md` — замеченные, но не исправленные баги.** Формат: симптом — где (`file:line`) — почему это баг — как воспроизвести (если понятно). **Не чинить по ходу.**

## Шаг 0 — обязательная страховка ПЕРЕД рефакторингом

Тестов нет, поэтому первым делом построй **сеть безопасности**, иначе любой рефакторинг — это игра вслепую:

- Настрой `pytest` (добавь в requirements-dev, создай `pyproject.toml`/`pytest.ini`).
- Напиши **характеризующие (characterization) тесты** на чистую бизнес-логику, которую легко изолировать без сети:
  - [bot/services/billing_service.py](../bot/services/billing_service.py) — `calc_earned`, `build_billing_rows` (обе групповые и индивидуальные ветки, остаток, деление на учеников).
  - [bot/utils/attendees.py](../bot/utils/attendees.py) — оба формата, round-trip parse↔serialize.
  - [bot/utils/dates.py](../bot/utils/dates.py), [bot/utils/ids.py](../bot/utils/ids.py), [bot/utils/lesson_stats.py](../bot/utils/lesson_stats.py).
  - [bot/services/visibility.py](../bot/services/visibility.py) — пересечение `teacher_groups ∩ student_groups` на фейковых репозиториях (in-memory стабы).
- Тесты фиксируют **текущее** поведение (даже если оно кажется странным) — это эталон, с которым сверяемся после каждого шага. Прогоняй `pytest` перед каждым коммитом.

Не начинай Шаг 1, пока чистая логика не покрыта тестами.

## Приоритизированный бэклог (по убыванию влияния)

Делай сверху вниз. Каждую задачу — отдельной веткой/серией коммитов, с обновлением тестов.

### P1. Вынести сквозные утилиты (быстрый выигрыш, низкий риск)
Дублируется по всему `bot/handlers/`:
- **Скопированные функции проверки прав.** `_is_admin()` определён заново в **9 файлах** (admin/bills.py:27, branches.py:29, client_requests.py:16, diagnostics.py:14, edit_lesson.py:27, profit.py:20, salaries.py:23, students.py:29, teachers.py:26), `_is_teacher()` — в **6 файлах** (teacher/my_groups.py:28, my_lessons.py:33, my_stats.py:17, partners.py:33, record_lesson.py:46, submit_period.py:27), плюс `_is_teacher_or_admin()` в my_lessons.py:37. За ними идёт один и тот же блок `if not _is_admin(user): await callback.answer("Нет доступа", show_alert=True); return` (~221 повтор глобально). Сделай **единый guard/aiogram-фильтр** (`IsAdmin`/`IsTeacher`) + один общий `_is_admin`/`_is_teacher` в [bot/handlers/common.py](../bot/handlers/common.py) и удали копии.
- **Форматирование денег** — повторяется в 11 файлах-хендлерах. Заведи `bot/utils/format.py::format_money(x) -> str` и замени все места.
- **`_MONTHS_RU`** (русские названия месяцев) продублирован в 4 файлах: [edit_lesson.py:21](../bot/handlers/admin/edit_lesson.py#L21), [my_groups.py:89](../bot/handlers/teacher/my_groups.py#L89), [my_lessons.py:27](../bot/handlers/teacher/my_lessons.py#L27), [client/my_bills.py:30](../bot/handlers/client/my_bills.py#L30). Сведи в `bot/utils/dates.py`.
- **`PAGE_SIZE = 20`** объявлен трижды: [bot/keyboards/admin.py:34](../bot/keyboards/admin.py#L34) (`_STUDENT_PAGE_SIZE`), [bot/handlers/teacher/my_lessons.py:25](../bot/handlers/teacher/my_lessons.py#L25), [bot/handlers/admin/edit_lesson.py:19](../bot/handlers/admin/edit_lesson.py#L19). Сведи к одной константе.
- **Безопасный ответ на callback** — вынеси общий helper для `callback.answer()` / `edit_text` с проглатыванием `TelegramBadRequest("message is not modified")` (сейчас `except Exception: pass` вокруг удаления/редактирования сообщений раскидан по [common.py:27,136](../bot/handlers/common.py#L27), [record_lesson.py:162,190](../bot/handlers/teacher/record_lesson.py#L162) и др.).
- Исправь рассинхрон документации: комментарий в [bot/repositories/base.py:8](../bot/repositories/base.py#L8) говорит «TTL 30 сек», а `_CACHE_TTL = 300`.

### P2. Общая абстракция для локеров-от-даблкликов
Сейчас **7 разных** module-level `set[str]` раскиданы по 6 файлам:
`_confirming_lesson_ids` ([record_lesson.py:41](../bot/handlers/teacher/record_lesson.py#L41)), `_submitting` ([submit_period.py:24](../bot/handlers/teacher/submit_period.py#L24)), `_sending`/`_group_sending` ([billing.py:32-33](../bot/handlers/teacher/billing.py#L32)), `_confirming_in_progress`/`_sending_in_progress` ([bills.py:23-24](../bot/handlers/admin/bills.py#L23)), `_group_send_in_progress` ([branches.py:535](../bot/handlers/admin/branches.py#L535)).
- Заведи один переиспользуемый async-контекстник, напр. `bot/utils/locks.py::once(key)` (context manager, который добавляет ключ в set на входе и **гарантированно снимает в finally**).
- Устрани риск неограниченного роста: ключи должны сниматься всегда, даже при исключении (сейчас часть снимается только в happy-path).

### P3. Хардкод бизнес-конфига → в конфиг/данные
Зашитые в код ID ломаются при любой смене персонала:
- `_PROXY_BUTTONS` с `TCH-0002 → TCH-0005/TCH-0008` ([bot/keyboards/teacher.py:6](../bot/keyboards/teacher.py#L6)).
- `BILLING_TEACHERS = {"TCH-0009"}` ([bot/keyboards/teacher.py:13](../bot/keyboards/teacher.py#L13)).
- PER_VISIT-группы и «магический» делитель `45` ([billing_service.py:13,53](../bot/services/billing_service.py#L13)).
Вынеси эти значения в одно место — `config/settings.py` (env) или отдельный конфиг-модуль с именованными константами. Значение `45` — именованная константа `MINUTES_PER_UNIT`. **Поведение не меняется**, меняется только место хранения.

### P4. Ввести сервисный слой между хендлерами и репозиториями
Хендлеры делают **403 прямых вызова** репозиториев (72 уникальных метода) — бизнес-логика размазана по UI-слою. Точечно, по одному сценарию за раз:
- Вынеси связки «прочитать несколько репо → посчитать → записать» из хендлеров в методы соответствующих сервисов (`LessonService`, `PaymentService`, и т.п. — см. таблицу сервисов в CLAUDE.md).
- Хендлер должен остаться тонким: распарсил callback → вызвал сервис → отрисовал результат.
- **Начни с самого грязного**: [bot/handlers/admin/students.py](../bot/handlers/admin/students.py) (например строки 900-990 — цепочки `student_repo` + `student_group_repo` + `set_partner` в теле хендлера).
- Не делай «большой сервис на всё» — добавляй ровно те методы, что нужны переносимому сценарию.
- **Эталонный кандидат:** `_render_student_card()` ([students.py:341-448](../bot/handlers/admin/students.py#L341), 107 строк) тянет **7 репозиториев** (`student_repo`, `teacher_repo`, `visibility`, `group_repo`, `branch_repo`, `student_group_repo`, `client_repo`) прямо в хендлере, чтобы собрать одну карточку. Вынеси сборку в `StudentService.get_student_card(...) -> StudentCardDTO`; хендлер только рисует DTO.

### P5. Декомпозиция файлов-«богов»
Три файла несоразмерно велики. Разбей по под-сценариям, сохранив публичные роутеры:
- [bot/handlers/teacher/record_lesson.py](../bot/handlers/teacher/record_lesson.py) — **1663 строки, 36 хендлеров, ~17 FSM-состояний**. Раздели wizard по стадиям (тип → выбор учеников/группы → дата → длительность → подтверждение), вынеси общие helpers (`_tid` и proxy-логику — сейчас `_tid` живёт только тут, хотя proxy используется и в admin). **Главная мишень:** функция `_finalize()` ([строки 1471-1663](../bot/handlers/teacher/record_lesson.py#L1471), **193 строки**, 4 ветки group/pair/shared/soloist + 5 except-блоков) — её бизнес-часть должна уехать в `LessonService`, а в хендлере остаться диспетчеризация по типу урока.
- [bot/handlers/admin/students.py](../bot/handlers/admin/students.py) — **1574 строки, 42 хендлера**. Раздели: CRUD ученика / партнёрства / связывание клиента / поиск.
- [bot/handlers/admin/branches.py](../bot/handlers/admin/branches.py) — **1031 строка, 34 хендлера**. Раздели: филиалы / группы / биллинг-режимы / массовая рассылка счетов.
- Каждый под-модуль экспортирует свой `Router`, агрегируется в существующих `__init__.py`. Callback_data и тексты — без изменений.

### P6. Обработка ошибок и логирование
- ~50 мест с широким `except Exception`. Не убирай их огульно (Sheets реально бросает разное), но: (а) логируй с контекстом, (б) где ловится конкретика (`TelegramBadRequest`, `gspread.exceptions.APIError`) — лови конкретику, а не всё подряд. Голых `except:` быть не должно.

## Метод работы (для каждой задачи бэклога)

1. Прочитай затронутый код целиком, пойми текущее поведение.
2. Убедись, что относящаяся логика покрыта характеризующим тестом (Шаг 0); если нет — сперва допиши тест.
3. Сделай минимальную изолированную замену.
4. `pytest` зелёный + `python -m bot` стартует без ошибок.
5. Отдельный коммит с осмысленным сообщением (по-русски, в стиле репо: «Extract …», «Introduce …»).
6. Переходи к следующему шагу. **Не смешивай задачи в одном коммите.**

## Критерии готовности

- Каждая задача бэклога — отдельная серия коммитов, `pytest` зелёный на каждом.
- Внешнее поведение бота идентично (тексты, кнопки, callback_data, суммы, порядок FSM).
- Нет ни одного нового прямого вызова gspread из хендлеров; новые связки репо+расчёт живут в сервисах.
- Дублирование из P1 устранено (единые `format_money`, `PAGE_SIZE`, admin-guard).
- Три файла-«бога» разбиты, ни один хендлер-файл > ~500 строк (ориентир, не догма).
- Ведутся и наполнены три файла-артефакта: `docs/BUSINESS_RULES.md` (каталог правил домена), `docs/IMPROVEMENTS.md` (идеи улучшений, не внедрённые), `docs/FOUND_BUGS.md` (баги, не исправленные) — все со ссылками `file:line`.

## Явные non-goals

- Не мигрировать с Google Sheets на другую БД.
- Не менять UX, тексты, эмодзи, структуру меню.
- Не добавлять фичи и не «улучшать» бизнес-правила.
- Не переписывать retry/cache стратегию репозиториев (только исправить неверный комментарий).
- Не деплоить.
