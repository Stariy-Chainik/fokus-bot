## Architecture

**Telegram bot** (aiogram 3) for a dance school CRM. **Google Sheets is the database** — every read/write goes through `gspread`. The bot has three roles: admin, teacher, and client (parent).

### Entry point & wiring

`bot/__main__.py` is the single DI container: it builds all repositories from one `SheetsClient`, wires them into services, and injects everything into the aiogram dispatcher via `dp["key"]`. Handlers receive dependencies as typed parameters (aiogram resolves them automatically).

Two middlewares run on every update:
1. **`DedupUpdateMiddleware`** — drops re-delivered Telegram updates (60s TTL window)
2. **`AuthMiddleware`** — loads `User` from `user_repo` and injects `data["user"]`; sets `None` if unknown

### Handlers

```
bot/handlers/
  common.py              # /start, role switching
  admin/
    teachers.py          # teacher CRUD, rates, period submission status
    students.py          # student CRUD, partnerships, requests
    salaries.py          # teacher earnings by period
    bills.py             # student invoices, send to parent
    branches.py          # branches, groups, teacher↔group assignment
    edit_lesson.py       # admin-only lesson edit/delete (bypasses period lock)
    diagnostics.py       # data integrity checks
    record_lesson.py     # admin proxy: record lessons on behalf of any teacher
  teacher/
    record_lesson.py     # FSM: record individual / pair / group lessons
    my_lessons.py        # view and delete own lessons
    submit_period.py     # lock period for billing
    my_groups.py         # group roster view
    partners.py          # manage pairs and soloists
  client/
    start.py             # client menu
    my_lessons.py        # lesson history for parent (what happened)
    my_bills.py          # invoices by month (how much to pay)
    payments.py          # Telegram Payments webhook handlers
```

Each file exports a single `Router`. Admin, teacher, and client routers are aggregated in their respective `__init__.py` and registered in `__main__.py`.

### Repositories

All inherit `BaseRepository` which wraps gspread in `asyncio.to_thread()`. Key behaviours:
- **TTL cache** (300 s) on all reads; invalidated on any write to that sheet
- **Retry** — 3 attempts with exponential backoff on HTTP 429/503

### Services

| Service | Responsibility |
|---|---|
| `LessonService` | Create/delete lessons; period-lock check; duplicate group lesson guard |
| `BillingService` | Pure functions: `calc_earned()` and `build_billing_rows()` |
| `PaymentService` | On-demand invoice computation; `get_or_create_invoices_for_student_period()` |
| `TeacherVisibilityService` | Which students/groups a teacher can see (via `teacher_groups` + `student_groups`) |
| `DiagnosticsService` | Cache/data health checks |

### Billing formulas

```
earned (teacher) = rate × (duration_min / 45)
  rate = rate_group          for group lessons
  rate = rate_for_teacher    for individual lessons

amount (student invoice) = rate_for_student × (duration_min / 45)
  split equally across all students in the lesson;
  first student absorbs the integer remainder

amount (PER_VISIT group) = group.price_full or group.price_short
  stored as snapshot in lesson.attendees at creation time: STU-001:60:700
```

Group lesson attendance is stored as a CSV in `lesson.attendees`:
`STU-001:60:700,STU-002:60:700` → parsed by `bot/utils/attendees.py`.

Two formats coexist:
- Old: `STU-001,STU-002` (no amounts → amount=0 → not billed)
- New: `STU-001:60:700` (with amount snapshot → billed)

### FSM

States are defined in `bot/states/`. Multi-step flows (record lesson, add teacher, edit rates, submit period) use aiogram FSM with explicit Back/Cancel buttons at each step. State is cleared on cancel or after successful completion.

**Admin proxy pattern**: `proxy_teacher_id` stored in FSM state allows an admin (or assistant) to record lessons on behalf of another teacher. Helper `_tid(user, data)` returns `data.get("proxy_teacher_id") or user.teacher_id`.

### ID format

All primary keys are human-readable sequential strings:
`TCH-0001`, `STU-0042`, `LES-000123`, `GRP-0001`, `BRN-001`, etc.
Generated by `bot/utils/ids.py` which scans existing rows for the current max.

## Key domain rules

- **Period submission** (`TeacherPeriodSubmission`): once a teacher submits a period, their lessons for that month are locked — no edits or deletes allowed except by admin.
- **Lesson names are denormalized**: `lesson.teacher_name`, `student_N_name` are snapshots at creation time. Renames do not rewrite history.
- **Teacher visibility** is derived from `teacher_groups` ∩ `student.group_ids` — there is no direct `teacher_students` table.
- **Multi-group students**: a student can belong to multiple groups; billing aggregates across all of them per period.
- **SHORT/FULL tiers** (`StudentGroupTier`): apply only to kindergarten groups (ЮБ/БП); all other groups have one price.
- **Group billing modes**: `NONE` (free, attendees not tracked for billing), `PER_VISIT` (each attended lesson is billed at group price), `SUBSCRIPTION` (not yet implemented).
- **NONE groups auto-save**: when recording a group lesson for a NONE-mode group, the attendance question is skipped and the lesson is saved immediately with `attendees=None`.
- **Duplicate guard**: `LessonService.create` blocks recording the same teacher+group+date twice.
- **Client vs Student**: a student attends lessons; a client (parent) pays. They are separate entities linked via `student.client_id`.
- **Client screens**: «Занятия» = lesson history (what happened, with per-lesson cost); «Счета» = invoices (how much to pay, payment button planned).

## Environment

Required vars (see `.env.example`):

- `GOOGLE_CREDENTIALS_JSON` — service account JSON (inline)
